# Design: Same-device pairing + app store distribution

## Problem Statement

naym currently requires two separate devices/sessions to run the ritual: partner A swipes, gets a link, sends it, partner B opens it on their own device. Real testing with friends and family surfaced friction: people sitting in the same room found the two-device coordination to be unnecessary ceremony. The founder wants a same-device "pass the phone" mode as an additional option (not a replacement — long-distance couples still need the link flow), plus wants to get naym onto the App Store and Play Store.

## What Makes This Cool

Passing a phone back and forth for a blind reveal, in front of the person who owns the app, is a more filmable, "whoa" moment than a solo link click — it's the couple performing the ritual together in real time instead of separately. It also removes the single biggest piece of setup friction between "I want to try this" and actually starting.

## Constraints

- Existing architecture is settled and adversarially reviewed (see [CLAUDE.md](../../CLAUDE.md) architecture invariants): server-enforced blindness boundary, monotonic swipe sync, B-slot binds only on explicit tap, pinned per-session deck snapshot, durable event log, dynamic app (no static export).
- Must support BOTH same-device and separate-device (link) modes going forward — this is additive, not a replacement.
- Project is explicitly a "fun side project," not a startup push right now — solutions should stay proportionate to that (no multi-week rewrites).

## Premises

1. The same-device gap is UX debt, not a validation failure — testers didn't reject the ritual, they rejected the setup ceremony. **Agreed.**
2. Same-device should be additive; the two-token session model, blindness boundary, and reveal logic all stay as-is. **Agreed.**
3. Most of the existing architecture (state machine, server-computed reveal, event log) doesn't care which physical device holds a token — a same-device mode is mostly a new handoff screen plus a lock on the transition. **Agreed.**
4. App store discovery for a brand-new, zero-review app was initially framed as the goal, which is a weak bet on its own (naym's own plan of record already settled on link-based virality as the primary distribution loop, and store ranking algorithms favor apps with existing installs/reviews). **Revised**: the founder's actual point is broader — app stores represent a real pool of potential customers who browse/search there, which Google/web search doesn't reach for an unranked new site either. This is legitimate: App Store category search has real high-intent traffic for new listings (title/subtitle keyword relevance matters more there than pure install velocity, more so on Apple's store than Google Play's). The efficient way to reach that pool is wrapping the existing web app, not rewriting it natively.

## Approaches Considered

### Approach A: Same-device mode + Capacitor-wrapped store listing (minimal viable) — CHOSEN
Add a "same phone" option at session creation. A swipes, hits a full-screen handoff card ("Hand the phone to your partner — don't peek"), B taps through and swipes, same server-computed reveal as today. Reuses the existing session/token model, swipe UI, reveal logic, and event log almost entirely; new surface area is a mode toggle + one handoff/lock screen. For stores: wrap the existing Next.js app with Capacitor (native shell loading the real hosted app) and submit to both stores — no backend rewrite, one codebase.

### Approach B: Shared-core rewrite into React Native/Expo (ideal architecture) — rejected for now
Extract session/swipe/reveal logic into a shared TS core, build a real Expo app alongside the web app. Real native gestures, push notifications, no "bare WebView" app-review risk. Rejected: a second frontend to maintain forever is disproportionate to a project explicitly framed as a fun side project right now. Revisit if naym gets real traction.

### Approach C: Same-device as hero flow, defer stores, chase social distribution — rejected for now
Make same-device the primary mode, skip app stores entirely, and lean on the shareable keepsake reveal card for Instagram/TikTok distribution instead. Rejected as the primary path because it doesn't answer the founder's actual want (store presence) — but the underlying idea (make same-device the more delightful default) is worth doing regardless of which distribution path is chosen.

## Recommended Approach

**Approach A.** It's the only one that answers both things the founder asked about — the pairing friction and store presence — without a rewrite or a bet-the-project distribution pivot. It ships fast, keeps a single codebase, and doesn't foreclose Approach B later if naym gets real traction.

## Open Questions

- Exact lock/reveal-prevention mechanism for the handoff screen (full-screen opaque card + explicit tap-through is the working assumption; needs a design pass to make peeking genuinely awkward, not just discouraged). If that design pass concludes a card-and-tap isn't enough, needs a fallback (e.g. a short countdown blackout) before Next Steps #1 is considered done.
- How A's and B's tokens coexist client-side within one same-device session. The link flow keys token storage per-device (one role per browser); same-device mode needs both roles live in one WebView instance. Working assumption: hold the active token in memory (not persisted storage), swap it on handoff, and clear A's from memory before B's swipe screen renders — needs confirming against the existing session client code before Next Steps #2 starts.
- Whether same-device sessions still round-trip through the API/Redis (for event-log consistency with the link flow) or can run lighter-weight since there's no cross-device sync need. Current lean: keep it going through the same API for event parity, with a `mode: "same-device" | "link"` field added to session/event records so the two flows stay analyzable separately, not just schema-compatible.
- **Real Apple review risk, named plainly:** the dominant rejection pattern for Capacitor/WebView wrappers is Guideline 4.2.3 ("minimum functionality" — not meaningfully different from a mobile browser). Icon, splash screen, and an offline error state do NOT address that criterion by themselves; only genuine native-feeling interaction does. Needs a concrete decision before submission: at least one real native touch (e.g. the existing keepsake reveal card going out through the native share sheet, or haptics on swipe) and a decision on local-bundle-plus-remote-API vs. full-remote-load (pointing the shell at a fully remote URL is the pattern most likely to trigger 4.2.3).
- App Store privacy "nutrition label" / data-use disclosure and age rating, **and** the Play Store equivalent (Data Safety form + IARC content rating) — required for both submissions, and worth thinking through deliberately here since the product handles two people's private preferences about each other.

## Success Criteria

- Same-device mode ships and a same-room couple can complete the full ritual on one phone without either partner seeing the other's picks early.
- App wrapped and submitted to both stores; passes Apple review on first or second submission.
- Play Store submission approved without a Data Safety or content-rating rejection cycle.

## Distribution Plan

Existing web app keeps its current deployment pipeline (Vercel + Upstash) unchanged. New: Capacitor-wrapped native shells for iOS and Android, submitted to the App Store and Play Store, pointing at the same hosted app. No new backend infra.

## Next Steps

1. Design the same-device handoff/lock screen (own the "don't peek" moment — this is the one new UI surface).
2. Add a mode toggle at session creation (same-device vs. link) that otherwise reuses the existing session API; resolve the client-side token-coexistence question above first.
3. Wrap the app with Capacitor; decide local-bundle-plus-remote-API vs. full-remote-load, and get a debug build running on a real device end-to-end.
4. Add at least one real native touch (native share sheet for the keepsake reveal card is the natural fit; haptics on swipe as a stretch) plus a real icon/splash and a friendly offline error state (not offline functionality — the app still needs a server). Skip push notifications for this submission; there's no real use case for them yet, and standing up APNs plumbing for an unused capability isn't worth the setup cost on a side project.
5. Prepare the App Store privacy label / data-use disclosure and age rating, and the Play Store Data Safety form + IARC content rating, before submission.
6. Submit to Play Store first (lighter review), then Apple App Store — budget for at least one 4.2.3 ("minimum functionality") rejection round-trip on the Apple side even with the native touches above.
